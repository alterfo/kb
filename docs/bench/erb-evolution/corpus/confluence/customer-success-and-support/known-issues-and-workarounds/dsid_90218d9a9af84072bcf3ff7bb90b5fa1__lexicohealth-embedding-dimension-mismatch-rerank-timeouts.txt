LexicoHealth: Embedding dimension mismatch causing rerank errors/timeouts (Known issue + workarounds)

h1. Summary
LexicoHealth experienced production errors and latency regressions on reranking shortly after a model catalog change that promoted a 1024-d embedding model. The immediate symptom was a vector length mismatch between query and candidate embeddings (512 vs 1024), leading to HTTP 4xx/5xx responses and tail latency timeouts on the rerank route.

This page documents the customer-facing symptoms, confirmed root cause, and the supported workarounds. It also summarizes the longer-term preventive work tracked in INT-1123.

h1. Customer + environment
* Customer: LexicoHealth (Enterprise)
* Environment: Redwood Hosted API, dedicated tenant
* Regions observed: us-west (primary), eu-west (failover)
* Affected endpoints:
** POST /v1/embeddings/encode
** POST /v1/rerank
* Models involved:
** open-embed-512-v1 (legacy 512-d)
** open-embed-1024-v2 (newer 1024-d)
** open-embed-default (alias)

h1. Symptoms
* Rerank requests returning errors and timeouts:
** Common message: "reranker: candidate vector length 512 != query vector length 1024"
** Increased 500/504 rate during peak traffic
* Increased latency on rerank calls (median +2–6s in the reported window) due to retries and error-path work
* Batch or async jobs failing validation when mixing stored 512-d vectors with newly generated 1024-d vectors

h1. What changed (high level)
On 2026-03-09, the model catalog was updated such that *open-embed-1024-v2* became the global default for content embeddings. LexicoHealth was relying on the alias *open-embed-default* to resolve to the legacy 512-d model (consistent with their existing stored embeddings and reranker expectations).

h1. Root cause (confirmed)
A catalog migration/promotion flow failed to persist tenant-specific alias overrides for a subset of tenants. For LexicoHealth, this caused *open-embed-default* to resolve to *open-embed-1024-v2* unexpectedly.

The reranker currently performs strict dimensionality checks and does not support automatic compatibility negotiation when provided embeddings from mixed dimensions. When it encounters a mismatch it:
* rejects the request or takes an expensive error-path that can include retries
* increases tail latency and contributes to timeouts under load

h1. Timeline (UTC)
* 2026-03-09 ~15:00: Customer-impacting behavior begins after catalog promotion
* 2026-03-10: Support escalation; SRE investigation identifies tenant alias drift
* 2026-03-10: Temporary routing override applied to force 512-d for LexicoHealth
* 2026-03-11: Hotfix prepared and rolled out to restore alias persistence
* 2026-03-13: Verification completed across affected tenants; monitoring continued
* 2026-03-20: This knowledge base entry updated with validated workaround steps and prevention plan

h1. Workarounds (supported)
h2. Workaround A (recommended): Pin embeddings model explicitly
Pin the embeddings model at the project/policy level so that calls using "open-embed-default" (or calls that omit a model) do not silently move dimensions.

*When to use:* customer has existing stored embeddings (512-d) and wants stable behavior.

Procedure:
# Set the project/policy to explicitly use *open-embed-512-v1* for embeddings.
# Restart or recycle any long-running workers that cache model metadata.
# Re-run the failing job batches created during the incident window (if they contain mixed embeddings).

Verification:
* Generate a new embedding and confirm vector length is 512.
* Submit rerank requests where both query and candidates are produced with the pinned model; confirm no mismatch errors.

h2. Workaround B: Regenerate embeddings to 1024-d (migration path)
If the customer intends to move to *open-embed-1024-v2*, the customer must ensure dimensional consistency:
* Re-embed the corpus to 1024-d
* Ensure the reranking pipeline uses 1024-d consistently (query + candidates)

*Important:* This is a customer-managed migration and may require reindexing/vector-store rebuild depending on their stack.

h2. Workaround C (temporary): Tenant-level routing override
Support/SRE can apply a tenant-level override to force the embeddings alias resolution.

*When to use:* emergency mitigation while the customer pins configuration or while waiting for catalog fixes to propagate.

h1. Current status (as of last_updated)
* The tenant alias persistence hotfix has been deployed and validated for LexicoHealth.
* For LexicoHealth, *open-embed-default* is confirmed to resolve to *open-embed-512-v1*.
* Global catalog default remains *open-embed-1024-v2* for new projects unless explicitly pinned.

h1. Prevention + follow-ups
The following improvements are planned/tracked:
* INT-1123: Implement a backward-compatible embedding adapter strategy in reranker (no silent conversions; clear behavior with explicit controls)
* Add catalog migration validation:
** Pre-deploy checks to confirm tenant alias overrides are preserved
** Post-deploy auditing + alerting on alias drift (per-tenant resolution diffs)
* Improve observability:
** Metrics for reranker dimension mismatch rejections
** Dashboards correlating catalog version changes to rerank error rates and tail latency

h1. Support playbook (for similar tickets)
* Triage questions:
** Are query embeddings and candidate embeddings generated by the same model version and dimension?
** Is the customer using an alias (e.g., open-embed-default) instead of an explicit model?
** Did the customer recently store embeddings that might now be mixed-dimension?
* Fast checks:
** Ask for one embedding sample output length from /v1/embeddings/encode
** Ask for the rerank error message (dimension mismatch is the key signature)
* Recommended response:
** Advise explicit model pinning
** If the customer needs to migrate to 1024-d, provide guidance on re-embedding and reindexing
** Escalate to SRE only if alias drift is suspected or overrides are required

h1. Notes specific to LexicoHealth
* LexicoHealth reported partial mitigation after pinning due to in-flight jobs created before the override propagated; restarting workers and re-running queued batches resolved remaining failures.
* If LexicoHealth opts into 1024-d in the future, coordinate a planned migration window to avoid mixed-dimension corpora.
