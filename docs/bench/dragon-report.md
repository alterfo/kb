# kb on DRAGON: русскоязычный RAG-бенч — отчёт по прогонам

Дата: 2026-08-29/30. Модель: `qwen3.8:latest` (27B, Q4_K_M) на ai-box для чата и
graph-extraction, `qwen3-embedding:0.6b` для эмбеддингов (query-time — локально,
index-time — на ai-box). `KB_LLM_NO_THINK=true` для всех прогонов ниже, кроме
первой (неудачной) попытки.

**Уточнение (2026-08-31):** на момент прогонов 1–2 `KB_LLM_NO_THINK` не был
переменной, которую читал код `kb` — это подтверждено `grep` по всей истории
git. Заявленное ускорение (157с/док → 17с/док) было реальным по факту, но
достигалось, по всей видимости, конфигурацией thinking-режима на стороне
Ollama/ai-box напрямую, а не переменной окружения в шелле `kb` (переменная в
локальном процессе не может повлиять на поведение удалённого сервера, если
код её нигде не читает и не передаёт в запрос). При повторной проверке
30.08.2026 thinking на ai-box снова оказался включён, и `KB_LLM_NO_THINK=true`
в шелле, как и ожидалось, ничего не изменил.
Разобрались и реализовали настоящий флаг: OpenAI-совместимый
`/v1/chat/completions`, который использует `kb`, **игнорирует** `think:false`
на Ollama — модель всё равно генерирует полное поле `reasoning`
(проверено curl'ом: 2.4с/95 токенов рассуждения что с флагом, что без).
Только нативный `/api/chat` реально уважает `think:false` (0.7с/0 токенов
рассуждения на том же промпте). `KB_LLM_NO_THINK` теперь — настоящий флаг
(`internal/config/env.go`, `internal/llm/chat.go`): при включении
не-стриминговые вызовы `Chat()` без tool-calls (это ровно то, что использует
графовая экстракция и GoT-синтез в индексации/бенче) идут через нативный
`/api/chat` с `think:false`; стриминг (`kb serve`/Ask) и tool-calling не
затронуты. См. README.

## Прогон 0: попытка на thinking-режиме (отменён)

Первая попытка `kb bench-dragon` (526 доков, thinking-режим по умолчанию)
зависла на 21+ минуте без единого признака прогресса. Расследование показало:
индексация без прогресс-лога + `qwen3.8` тратит реальное время на chain-of-thought
даже перед тривиальным ответом. Прямой замер: **157 с/документ** на извлечение
графа с thinking включённым.

Добавлен прогресс-лог (`indexed N/M`, `answered N/M` каждые 25). С thinking,
отключённым на тот момент (см. уточнение выше): **~17 с/документ** (~10x).

## Прогон 1: plain-корпус (526 текстов / 600 вопросов), self-eval

`docs/bench/dragon-answers.json` — `kb bench-dragon` (без `--hist`), полный
граф, `KB_LLM_NO_THINK=true`, concurrency=3.

- Индексация: 526 доков за ~2.4ч (~16.7 с/док).
- Ответы: 600 вопросов за ~7.9ч (~47 с/вопрос).
- Итого: ~10ч20м, 0 пустых ответов, 0 нулевых found_ids.
- Ручная проверка на реальных текстах: **5/5 выборочных ответов подтверждены**
  дословно по исходным статьям (два случая выглядели подозрительно при обрезке
  текста до 500 символов — при чтении полного текста оба оказались абсолютно
  точны).

Публичный набор вопросов `ai-forever/rag-bench-public-questions` не содержит
эталонных ответов — это **self-reported** результат, не официальный скор.

## Прогон 2: hist-корпус (542 текста / 600 вопросов), реальный скоринг

`docs/bench/dragon-hist-answers.json` — `kb bench-dragon --hist`, те же настройки.

Причина отдельного прогона: официальный (ungated) golden-датасет
`ai-forever/hist-rag-bench-private-qa` (600 пар вопрос-ответ с `text_ids`)
привязан к `hist-*` версии корпуса, а не к той, что использована в Прогоне 1
(разные тексты, разные вопросы под одними и теми же id — проверено напрямую).

- Индексация: 542 дока за 2ч14м.
- Ответы: 600 вопросов за ~7.5ч.
- Скоринг: `kb bench-dragon score` (`internal/bench/dragon/score.go`,
  Go-скорер, без Python) — join по `public_id`, метрики:
  `retrieval_hit` (пересечение `found_ids` с золотым `text_ids`) и
  `answer_contains_gold` (все словоформы золотого ответа найдены среди
  словоформ ответа kb после приведения к основе — см. ниже; для типа `set`
  — так проверяется каждый элемент списка).

### Итоговые числа (`docs/bench/dragon-hist-score.json`)

| Тип вопроса | n | answer_contains_gold | retrieval_hit* |
|---|---|---|---|
| cond (условные) | 150 | 136 (90.7%) | 6 (4.0%) |
| mh (multi-hop) | 150 | 113 (75.3%) | 3 (2.0%) |

### Скоринг: substring-match → сопоставление по основам слов (с учётом порядка)

Первая версия скорера сравнивала золотой ответ с ответом kb буквальным
substring-совпадением (после `strings.ToLower`). Для русского языка — сильно
флективного — это давало массовые ложные срабатывания «неверно» там, где
модель отвечала по существу правильно, но в другом падеже/числе: например,
золотой ответ `Израиль`, ответ kb — «...проживает **в Израиле**» (не
substring друг друга), или золотой список `['Великобритания', 'США',
'Франция']` против ответа «обогнала США, **Великобританию** и **Францию**»
(винительный падеж вместо именительного — для `set`-типа одно
несовпавшее слово из списка обнуляет весь вопрос).

Официальный скрипт DRAGON (`lib/src/rag_bench/evaluator.py` в
`RussianNLP/DRAGON`) считает генерацию через ROUGE-1/2/L с русским
`SnowballStemmer`, а не буквальным substring — то есть первая версия нашего
скорера была строже официальной методики именно из-за морфологии.

Первая попытка исправления (`internal/bench/dragon/score.go`) токенизировала
золотой и модельный ответ, приводила каждое слово к основе через
`github.com/kljensen/snowball/russian` и проверяла, что каждая основа
золотого ответа (или элемента `set`-списка) нашлась **где угодно** среди
основ ответа модели — без учёта порядка слов (bag-of-stems). Это подняло
скор с 67,0% до 80,0%, но ревью на `revmux` (профиль `comprehensive`)
обнаружило реальный побочный эффект: множественное слово теряло смежность —
золотой ответ `Северная Корея` засчитывался верным, даже если «северная» и
«корея» встречались в разных, не связанных предложениях ответа. Часть роста
67,0%→80,0% была метрическим артефактом второго рода (переоценка, а не
недооценка).

Исправлено: `phraseStemsPresent` теперь требует, чтобы основы слов золотой
фразы шли в ответе модели **смежной последовательностью** (sliding-window
по стеммированным токенам ответа), а не просто присутствовали где-то в
тексте — так сохраняется устойчивость к падежным окончаниям без потери
информации о порядке слов. Пересчёт того же `dragon-hist-answers.json`
(всё ещё без повторного 10-часового прогона LLM) дал **финальный, честный
результат: 451/600 (75.2%)** — между исходными 67,0% (слишком строго,
штрафует за падеж) и промежуточными 80,0% (слишком мягко, теряет порядок
слов). Разница 480→451 (29 вопросов) — в основном `set` (110→97) и
`simple` (114→105), где многословные ответы/элементы списка чаще всего
собирались из разбросанных по тексту слов.

### Почему retrieval_hit низкий, хотя ответы верны

DRAGON — новостной корпус: один и тот же факт часто освещён в нескольких
статьях (синдикация/дубли). Золотой `text_ids` указывает ровно на ОДНУ
каноническую статью на факт; kb вправе (и часто) находит и честно цитирует
**другую** реальную статью с тем же фактом.

Количественная проверка: из 402 верных ответов 391 (97%) не попали в
canonical `text_ids` — но во всех 391 случаях документ, который kb сам
процитировал в ответе, **реально присутствовал в `found_ids`** (0 случаев
галлюцинированной ссылки на неретрив­нутый документ). Значит: `retrieval_hit`
в текущем виде — артефакт метрики (один канонический id на факт), а не
дефект поиска kb. Честная метрика поиска здесь — «процитированный документ
существует и был ретрив­нут» (100% в проверенной выборке), а не «совпал с
единственным golden id».

## Найденные и исправленные баги скорера (не в kb, в новом Go-коде)

1. **`set`-тип**: золотой `answer` хранится как Python-repr списка
   (`"['Педагог', 'Музыкант']"`), а не как обычная строка. Первая версия
   скорера делала прямой substring-check по всей строке (включая скобки и
   кавычки) и всегда возвращала 0/150.
   Исправлено: детект `[`/`]`-обёртки, извлечение элементов через regex,
   ответ засчитывается верным только если присутствуют ВСЕ элементы
   (строго, без частичного зачёта). После фикса: 0/150 → 82/150.
2. Флаг-парсинг: `kb bench-dragon score` требует флаги ДО позиционного
   аргумента (`flag`-пакет Go останавливает парсинг на первом non-flag).
3. **Морфология**: буквальный substring-match не учитывал русские падежные
   окончания — см. раздел «Скоринг: substring-match → сопоставление по
   основам слов (с учётом порядка)» выше. Сопоставление по стемам без учёта
   порядка слов (Snowball, bag-of-stems): 67,0% → 80,0% — но переоценивало
   многословные ответы (терялась смежность). С учётом порядка (sliding-window
   по стеммированным токенам): финальные 75,2%.

## Артефакты в репозитории

- `docs/bench/dragon-answers.json` — self-eval прогон (plain, 526/600).
- `docs/bench/dragon-hist-answers.json` — прогон с реальным скорингом (hist, 542/600).
- `docs/bench/dragon-hist-score.json` — итоговый отчёт скорера.
- `internal/bench/dragon/` — загрузчик HF, конвертер, раннер, сабмишен, скорер (41 тест).
- `cmd/kb/dragon.go` — `kb bench-dragon [--hist] [--limit N] [--concurrency N]`,
  `kb bench-dragon score <answers.json>`.

**See also:** `docs/bench/actualization-report.md` — тот угол, который DRAGON
показать не может: как ответы меняются после прихода новых сообщений в чат
(temporal-актуализация: `superseded_by` на чанках, закрытие `valid_to` у старых
связей), тогда как DRAGON — статичный one-shot корпус без обновлений.

## Оставшийся разрыв (~25%, 149 вопросов) и рычаги для второго раунда

Прогон делался с конфигом по умолчанию: `KB_RERANK=off`, `KB_QUALIFIER_FILTER=false`.
Ручной разбор оставшихся провалов показывает три разные причины, не связанные
с метрикой:

1. **Retrieval miss** — нужный документ есть в корпусе, но не попал в top-K
   контекста (модель честно отвечает «в источниках нет информации»).
2. **Неполное перечисление** для `set` — часть элементов списка названа,
   часть пропущена.
3. **Неверная трактовка вопроса** — узкая интерпретация неоднозначной
   формулировки (например, «с кем встречался» прочитано как «с кем был в
   личных отношениях» вместо дипломатической встречи).

Кандидаты на второй раунд: включить реранкер (`KB_RERANK=llm`/`onnx`),
поднять `KB_MAX_SUBGOALS`/`KB_MAX_GAP_QUERIES`/`KB_CANDIDATE_K` для
multi-hop, проверить `KB_QUALIFIER_FILTER=true` на предмет recall
именованных сущностей. 100% не рассматривается как цель: часть провалов —
шум/неоднозначность самого golden-сета, а честная абстеенция при
отсутствии данных — осознанный компромисс (0 галлюцинированных цитирований
в проверенной выборке), которым не стоит жертвовать ради последних процентов.

## Не сделано / открытые вопросы

- Официальная заявка в лидерборд DRAGON (`ai-forever/rag-leaderboard`) требует
  Python-клиента `rag-bench` с live-вызовом ретривера/генератора — не
  реализовывалось (не Go, требует отдельного решения об интеграции).
  Данный отчёт — независимый локальный скоринг против того же golden-сета,
  который использует официальный лидерборд, но не является официальной заявкой.
- `retrieval_hit` можно сделать честнее, посчитав «процитированный документ
  реально ретрив­нут» как отдельную метрику по всем 600 вопросам (сейчас
  посчитано только для верно отвеченных, как точечная проверка гипотезы).
- Нет `--persist-dir`: каждый прогон переиндексирует корпус с нуля даже если
  документы не менялись между запусками.
